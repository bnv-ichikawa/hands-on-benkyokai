# 🧑‍💻 エンジニアに期待すること

この文書は、BNV Ops Platform の開発に参加する社内エンジニア・業務委託エンジニア向けです。

共通する考え方は [AI時代の仕事とプロダクトづくりの原則](./README.md) を正本とします。

## 🎯 実装ではなく、課題解決に責任を持つ

エンジニアの仕事は、Issue や依頼文をコードへ変換することだけではありません。システムやコードは、業務上の課題を解決するための手段です。

利用者、業務フロー、データ、例外、前後の作業、運用を理解し、何を解くべきかを考えてください。

### 依頼された「方法」を、そのまま要件にしない

利用者から提示される解決案には、本来達成したい業務上の目的と、実現方法の仮説が混在することがあります。

依頼の背景と目的を確認し、**達成したいことと実現方法を分けて考えます。** 必要であれば、依頼された方法とは異なる方法や、「作らない」という選択肢も提案してください。

### 仮説を持ち、小さく検証する

すべての情報が揃うまで待つのではなく、現時点の情報から仮説を置きます。

AI、データ、ログ、簡易プロトタイプ、ヒアリングなどを使い、重要な不確実性から小さく検証してください。AIによって検証コストが下がるほど、**何を検証すべきかを考える力**が重要になります。

期待する流れは、**課題理解 → 仮説 → 検証 → 設計 → 実装 → 利用結果の確認**です。

コードが動くことは完成条件の一部にすぎません。品質、保守性、セキュリティ、運用負荷、障害時の挙動、将来変更まで含めて専門家として判断してください。

## 🧠 AIで実装速度だけでなく、判断の質と速度を上げる

AIは、コーディングだけでなく、調査、設計案の比較、プロトタイピング、テスト、レビュー、データ分析にも使います。

AIに作業を任せるほど、エンジニアには次の価値が求められます。

- 問うべき課題を見つける
- 業務文脈を踏まえて仮説を立てる
- 重要な不確実性から検証する
- AIや調査結果の妥当性を評価する
- 複数の選択肢から適切な判断をする
- 利用者や一緒に働く人が判断しやすい形で伝える
- 最終的な成果物を説明し、責任を持つ

AIが生成した成果物を、本人が理解・検証せずそのまま提出することは、専門家としての仕事とは考えません。

## 🛠️ モノづくりのスタンス

### 👥 社内・業務委託エンジニア共通

開発成果だけでなく、日々の進め方を次の4つのスタンスで見ます。

| スタンス | 期待する行動 |
|---|---|
| **💙 Client First** | システム都合ではなく利用者と業務目的から考える。Slack、資料、PRも、受け手が理解・判断し、次の行動を取りやすい形にする。 |
| **🤝 Commitment** | 合意した成果と期限に責任を持つ。前提変更や遅延リスクは早く共有し、影響と選択肢を整理して再合意する。 |
| **🧭 Professionalism** | 品質、保守性、拡張性、セキュリティ、運用負荷を踏まえて専門家として判断する。「AIがそう言った」「依頼されたから」だけを判断根拠にしない。 |
| **🚀 Be Proactive** | 明示された依頼だけを待たず、課題や改善余地を発見して提案する。ただし、合意なくスコープを広げない。 |

### 🏢 社員エンジニアのみ

社員エンジニアには、上記4つに加えて **Global** を適用します。

| スタンス | 期待する行動 |
|---|---|
| **🌏 Global** | 目の前の一件だけでなく、会社全体、将来、世界水準から考える。現在の慣習や局所最適に閉じない。 |

## 📈 評価の考え方

成果物の量や作業時間だけでは評価しません。

社内・業務委託エンジニアには共通の4スタンスを用い、社員エンジニアには **Global** も加えて、**限られた時間とリソースから、会社にどれだけ良い結果を生み出したか**を見ます。

AIによって同じ成果をより短時間で実現できることは望ましい変化です。その余力を、より重要な問題の発見、仮説検証、品質向上、新しい価値の創出へつなげることを期待します。

忙しく見えることや長時間働くことではなく、AIを活用しながら、人が課題設定・仮説・判断・コミュニケーション・責任に時間を使い、より大きな成果を生み出すことを評価します。
