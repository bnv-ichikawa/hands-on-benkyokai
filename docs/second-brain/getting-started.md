# Second Brain を始めるときに決めること

Second Brain のまとめ方に、全員に共通する唯一の正解はありません。扱う情報、探し方、更新頻度、AI の使い方は人によって異なります。

このページでは、最初から細かいルールを押し付けるのではなく、利用者が自分に合った運用を決めるために、開始時に考えることを順番に整理します。最初は仮のルールで構いません。実際に使い、困ったところだけ見直します。

## 1. 何のために使うかを決める

最初に、Second Brain を使って何を改善したいかを言葉にします。

例:

- プロジェクトの背景や判断理由を、あとから確認できるようにしたい
- 会議の決定事項と次のアクションを見失わないようにしたい
- 調査や学習を、一度きりで終わらせず再利用したい
- AI に毎回同じ前提を説明しなくてもよい状態を作りたい
- 過去のメモから、文章、企画、設計などの成果物を作りたい

目的は1つから3つ程度で十分です。目的が曖昧なまま情報を集めると、保存すること自体が作業になりやすくなります。

## 2. 管理する範囲を決める

仕事、学習、生活など、どの範囲をこのワークスペースで扱うかを決めます。

例:

| 方針 | 管理するもの |
| --- | --- |
| 仕事だけ | プロジェクト、会議、調査、判断記録 |
| 学習だけ | 読書、記事、動画、講座、学んだこと |
| 仕事と生活 | 仕事に加えて、健康、家計、旅行など |

範囲を広げすぎると、置き場所や公開範囲の判断が難しくなります。最初は、利用目的に直結する範囲だけで始めます。

## 3. 保存しない情報を決める

保存するものだけでなく、保存しないものも先に決めます。

例:

- パスワード、API キー、アクセストークン
- GitHub や AI に渡してはいけない機密情報
- 保存する必要のない個人情報や顧客情報
- 権利や利用条件を確認していない外部資料の全文
- すぐに古くなり、参照する価値が残らない一時情報

外部資料は、ファイルそのものを保存する前に、要約と出典リンクだけで目的を満たせないか検討します。

## 4. 情報の置き場所を決める

このテンプレートでは、Inbox と PARA を出発点にします。

| 場所 | 判断基準 |
| --- | --- |
| `inbox/` | まだ整理していない、または置き場所を決めていない |
| `projects/` | 完了条件や成果物がある |
| `areas/` | 継続的に維持・改善する責任がある |
| `resources/` | 将来参照する知識や資料である |
| `archives/` | 完了、停止、または現在は使わない |

迷った場合は、無理に分類せず `inbox/` に置きます。運用を始めてから、自分に不要な分類を使わない、独自の分類を追加する、といった調整をしても構いません。

## 5. 好みのまとめ方を決める

あとで読み返しやすい形は人によって異なります。次の項目から、必要なものだけ決めます。

### ノートの長さ

例:

- 1ファイルに1つの主張や要点だけを書く
- 会議やプロジェクト単位で、関連情報を1ファイルにまとめる
- 最初に短い要約を書き、その下に詳細を残す

### ファイル名

例:

- 内容が分かる英語名: `project-decisions.md`
- 日本語名: `プロジェクトの判断記録.md`
- 日付を含める: `2026-07-26-meeting.md`

同じディレクトリでは、できるだけ同じ命名方針を使います。

### メタデータ

必要な場合だけ、Markdown の先頭に frontmatter を付けます。

```md
---
tags:
  - example
freshness: current
source_notes: []
---
```

すべてのノートに同じ項目を強制する必要はありません。検索、更新判断、出典確認に役立つ項目だけ使います。

### 事実と自分の考え

調査結果、引用、会議で決まったことと、自分の解釈や提案を区別します。

例:

```md
## 確認できたこと

## 自分の解釈

## 次に確認すること
```

### 情報同士のつなぎ方

例:

- 本文中に関連ノートへのリンクを置く
- 各ディレクトリの `README.md` を目次として使う
- ノートが増えてから MOC や索引を作る

最初からすべてのノートを細かくリンクする必要はありません。探しにくさを感じた時点で追加します。

## 6. 日常の運用ルールを決める

次の項目について、無理なく続けられるルールを決めます。

### 情報を捕まえる場所

例:

- 思いついたことは、まず `inbox/` にMarkdownで残す
- 会議メモは会議直後に `inbox/` に保存する
- 外部サービスの情報はコピーせず、URLと要点を残す

### Inboxを整理するタイミング

例:

- 毎週金曜日に確認する
- ファイルが10件を超えたら整理する
- プロジェクトで必要になったときだけ整理する

### 整理したあとの扱い

例:

- 元のメモを残す
- 必要な知識だけ別ノートにし、元のメモは削除する
- 元のメモを `archives/` に移す

`inbox/` は初期設定では Git の管理対象外です。共有するノートから、手元にしか存在しない Inbox ファイルだけを参照しないよう注意します。

### 古い情報の扱い

例:

- プロジェクト完了時に `archives/` へ移す
- 日付や制度に依存する情報へ `freshness: current` を付ける
- 古い可能性がある情報を確認したら `freshness: stale` にする
- 半年に1回、Areaと重要なResourceを見直す

### AI に任せる範囲

例:

- 読み取り、検索、要約は確認なしで依頼する
- ファイルの作成・更新は提案を確認してから行う
- 移動、上書き、削除は必ず事前に確認する
- AI の推測は事実として保存しない

## 7. 最初のノートで流れを試す

ルールを決めたら、実際の情報を1つだけ使って流れを試します。

1. メモを `inbox/` に置く
2. 要点、判断、アクション、再利用できる知識を抽出する
3. PARA のどこに置くか決める
4. 必要なノートを作る
5. 元情報と関連ノートをリンクする
6. 数日後に、目的の情報を見つけられるか確認する

うまく分類できなかった場合は、ノートを責めるのではなく運用ルールを見直します。

## 開始時の設定メモ

決めた内容は、ルートの `README.md` や自分用の運用方針ファイルに残します。次の形をコピーして使えます。

```md
# Second Brain 運用方針

## 目的

- 

## 管理する範囲

- 

## 保存しない情報

- 

## ノートのまとめ方

- 

## Inboxを整理するタイミング

- 

## Archiveへ移す基準

- 

## AIに任せる範囲

- 

## 見直すタイミング

- 
```

この設定も固定ではありません。使いにくさが出たときに変更し、現在の運用と文書の内容を一致させます。
