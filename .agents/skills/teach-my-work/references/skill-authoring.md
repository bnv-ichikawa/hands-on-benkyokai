# 業務をSkillにする

このファイルは、業務ナレッジをAI実行用のSkillへ変えるときだけ読む。

## 目標

合格ラインは、**新しいAIセッションが、以前の会話を読まずにSkillだけで業務を進められること。**

そのために、Skillの入口には次を短く書く。

- 何を達成するSkillか
- いつ使うか、使わないか
- 必要な入力・開く場所・参照情報
- 実行後に確認する完了条件
- `STEP 1`、`STEP 2` の順に並べた標準手順

画面名、URL、ファイル、入力値、判断基準、例外、確認方法は、AIが補完せずに動ける粒度で具体化する。

## 分け方

**1ページ（1ファイル）には1つの目的だけを書く。** 入口の `SKILL.md` は、全体の標準手順と参照先を案内する。

- 分岐がある場合: 条件を入口に書き、詳細を `references/<分岐名>.md` へ分けてリンクする
- 手順の補足が長い場合: 実行する場所・目的ごとのページに分ける
- 会社共通の用語、判断基準、制度、参照資料: Second Brainを正本にし、Skillからリンクする

同じ説明を複数のSkillや複数ページへ写さない。情報を直す場所が増えると、古い説明と新しい説明が混ざる。

## 冗長さを削る

AIに長文の整理を任せるだけでは、同じ前提を言い換えて繰り返すことがある。各段落が「次の操作」「判断」「参照先」「完了確認」のどれにも役立たないなら削るか、必要なページへ移す。

- 重複はトークンを消費し、AIの優先順位を曖昧にする
- 人間にとっても、読む・直すコストが増える
- CodexやClaude Codeでは長いSkillを扱えても、MyGPTなどへ移植すると文字数制限に当たることがある

短くするために、判断基準や例外を消してはいけない。削る対象は説明の重複であり、実行に必要な条件ではない。

## 新しいAIでのテスト

Skillを保存したら、会話の文脈を持たないAIへSkillだけを渡す。

1. AIに「このSkillだけを根拠に業務を実行して」と依頼する
2. AIが必要な入力、操作、判断、例外、完了確認を自力で辿れるかを見る
3. AIが質問した・誤った・推測した箇所を、Skillの不足として記録する
4. 不足を直し、必要なら再テストする

テスト中のAIが追加情報を求めたときは、その場で口頭補足して終わらせない。補足内容をSkillまたは参照先へ反映する。
