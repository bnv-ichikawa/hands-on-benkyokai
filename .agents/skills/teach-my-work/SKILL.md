# Teach My Work

ユーザーの業務を、再利用できる業務ナレッジへ変える。

このファイルは**入口**である。共通の前提と進め方の選択だけを扱い、実際の手順は選ばれた1つの手順書に書いてある。

## 1. 最初のメッセージで4つ聞く

**いきなり質問を始めない。いきなりファイルを探しに行かない。** 次の4つを**1回のメッセージ**でまとめて聞く。

1. **どの業務の話か**（1〜2行で）
2. **材料はあるか**（メモ、議事録、Slack や Notion のログ。あればその場所。無ければ会話から作る）
3. **どの進め方にするか**（下の「進め方」の表を見せる）
4. **何のために残すか**（下の「用途」の表を見せる）

### 進め方

**ここを飛ばして質問を始めない。** 材料があるのにAIが一から聞くのも、材料が無いのにAIが待つのも、どちらも時間の無駄になる。

| 進め方 | どう進むか | 向いている場面 |
| --- | --- | --- |
| **メモ起点型** | 材料を読み、3行で要約して読み違いを潰してから、書かれていない前提と判断基準を質問する | 議事録や手順メモがすでにある。`inbox/` を整理したい |
| **ヒアリング型** | 材料なし。AIが目的 → 開始と完了 → 手順 → 判断基準 → 例外の順に質問して引き出す | 何も書いていない。何から話せばいいか分からない |
| **語り起こし型** | 先に本人が思い出した順で全部話す。AIは遮らず記録し、区切ってから整理の仕方に論点を移す | 言いたいことは頭にあるが、順番に整理されていない |

決まらない場合は、材料があるなら**メモ起点型**、無いなら**ヒアリング型**を既定にし、理由を一文添える。

### 用途

**ここを曖昧にしたまま進めない。** 誰が読むかで、書く粒度と省いてよいことが変わる。

| 用途 | 読者 | 書き方への効き方 |
| --- | --- | --- |
| 自分とAIが後で再利用する | 未来の自分 | AIが読む前提の書き方にする。前置きより手順と条件を先に置く |
| 誰かに引き継ぐ | その業務の初任者 | 社内用語の説明を入れる。なぜそうするかを添える |
| チームで共有する | 同僚 | 個人の進め方と、組織の標準を分けて書く |

用途で変わるのは**書き方**だけである。**掘る深さは用途によらず「到達基準」で固定する。**

置き場所そのものは用途では決めず、「配置」の基準で決める。

## 2. 選ばれた手順書だけを読む

| 選択 | 読むファイル |
| --- | --- |
| メモ起点型 | [flows/from-notes.md](flows/from-notes.md) |
| ヒアリング型 | [flows/interview.md](flows/interview.md) |
| 語り起こし型 | [flows/braindump.md](flows/braindump.md) |

**選ばれた1つだけを読む。3つ全部読まない。** 以降はその手順書に書かれた段階に従う。

途中で「そういえば元のメモがあった」「質問される方が楽」「もう全部話したい」と言われたら、その時点で該当の手順書を読み、**いま聞き取った内容を引き継いで**切り替える。最初から聞き直さない。

## 到達基準

**どの進め方でも、掘る深さの合格ラインは1つ。**

> **このノートだけを渡されたAIが、次回この業務を実行できる。**

読んで理解できる、では足りない。**実行できる**まで掘る。行間を補える人にしか使えないノートは、Second Brain として再利用できない。

自分用だから省いてよい、とはしない。半年後の自分は、AIと同じくらい文脈を失っている。

### 実行できる状態の7要素

手順の各ステップについて次が埋まっているかを見る。埋まっていない箇所が深掘りの対象になる。

| 要素 | 埋まっている | 足りない |
| --- | --- | --- |
| 入力 | 「#請求 チャンネルに届く申請フォームのリンク」 | 「依頼が来たら」 |
| 場所 | 「Notion の請求管理DB」＋URL | 「管理シート」 |
| 操作 | 「金額列に税抜金額を入れ、状態を確認中にする」 | 「情報を登録する」 |
| 判断 | 「税抜50万円以上なら部長承認。未満は自分で確定」 | 「金額が大きければ承認をもらう」 |
| 出力 | 「PDFを1枚書き出し、先方の経理担当へメール添付」 | 「相手に送る」 |
| 検証 | 「状態が完了になり、Slack に自動通知が出る」 | 「問題なければ終わり」 |
| 例外 | 「差し戻されたら〜。判断できないときは〜の役割の人に聞く」 | 「エラーが出たら対応する」 |

固有名詞、閾値、システム名は具体的に書く。ただし「安全確認」の基準に触れるものは役割名へ置き換え、**置き換えたことをノートに明記する。**

### 曖昧語が残っていたら、まだ掘れていない

次の表現をそのまま書かない。出てきたら質問する。

適宜 / 状況に応じて / 基本的に / 必要に応じて / いい感じに / しっかり / ちゃんと / 適切に / 随時 / だいたい / ケースバイケース

次の動詞は、**誰に・何を・どこで**が付いていなければ実行できない。

確認する / 共有する / 連携する / 調整する / 精査する / すり合わせる / 巻き取る / 対応する

### 掘るのをやめる条件

項目ごとに、次のどれかを満たしたら止める。

- 7要素が埋まった
- ユーザーが「不明」「決まっていない」と答えた → 未確認事項に書く
- ユーザーが「その都度違う」と答えた → **何を見て判断しているかを1回だけ追加で聞く。** それでも出なければ未確認事項に書く
- 掘っても業務の成否が変わらない（使うブラウザの種類など）

**分からないことをAIが埋めて完成させない。** 穴が空いていると分かる状態のほうが、埋まったふりより価値がある。

### 1回のセッションで終わらなくてよい

解像度が足りないまま完了と報告しない。ただし1回で終わらない場合は、そこまでの内容を保存し、ノートの「次に確認すること」に**足りていないステップと、誰に聞けば埋まるか**を書いて中断する。次回はそこから再開する。

中途半端な状態で終わるときは、ユーザーにそう伝える。完成したように見せない。

## 材料の扱い

- **材料の指定がない呼び出しでは、材料は無いものとして扱う。** ディレクトリを探しに行かない
- 場所を指定された場合だけ、それを読む。見つからなければ探索範囲を広げず、場所を1回聞く
- `second-brain/inbox/` を見に行くのは、ユーザーが「inbox を整理して」「あのメモから」のように**そこにある前提で話したときだけ**
- 外部サービス（Notion、Slack、Google Drive など）が正本の情報は、全文を写さず要点と出典リンクだけを残す
- 会話だけで進める場合、聞き取った内容がそのナレッジの唯一の材料になる

## 安全確認

材料に認証情報、個人情報、顧客の機密情報がないか確認する。見つけた場合は内容を引用せず、匿名化または除去を依頼して作業を止める。

判断基準は [getting-started.md](../../../docs/second-brain/getting-started.md) の「3. 保存しない情報を決める」を使う。

**聞き取りの途中で出てきた場合も同じ扱いにする。** 会話で聞いたことだから保存してよい、とはしない。

## 聞き方の決まり

進め方によらず、質問はこのルールで行う。

- 一度に**最大5問**。成果に影響する不足から聞く
- 答えを誘導しない。「〜ですよね？」と確認する形にしない
- 「不明」「決まっていない」と答えられる形にする。答えられなかった項目は未確認事項として残す
- 業務の言葉をそのまま使う。AIの用語に言い換えて質問しない
- ユーザーの答えをAIの推測で埋めない

埋めたい項目は次の10個。これを `確認済み / 不足 / 矛盾` に分けて持ち、質問のたびに更新する。

目的、開始条件、完了条件、標準手順、判断基準、例外、失敗時の対応、責任範囲、根拠資料、情報の鮮度。

このうち **開始条件、完了条件、標準手順、判断基準、例外** の5つは、「到達基準」を満たすまで掘る。**この5つを用途の都合で省かない。** 掘った結果ユーザーが答えられなかったものだけを、未確認事項として残す。

残り5項目は、業務の成否に効く範囲で聞く。鮮度は frontmatter の `freshness` に反映する（[getting-started.md](../../../docs/second-brain/getting-started.md) の「古い情報の扱い」）。

## 配置

[getting-started.md](../../../docs/second-brain/getting-started.md) の「4. 情報の置き場所を決める」に従って置き場所を決め、各ディレクトリの `README.md` で判断基準を確認する。

- [`second-brain/projects/`](../../../second-brain/projects/README.md) — 期限、成果物、完了条件がある
- [`second-brain/areas/`](../../../second-brain/areas/README.md) — 継続的に維持・改善する責任がある
- [`second-brain/resources/`](../../../second-brain/resources/README.md) — 将来参照する知識や資料である
- [`second-brain/archives/`](../../../second-brain/archives/README.md) — 完了、停止、または現在は使わない
- 判断できない場合は `second-brain/inbox/` に残し、何が決まれば動かせるかを書く

PARA の考え方の背景は [second-brain.md](../../../docs/second-brain/second-brain.md) の「整理の考え方: PARA」にある。同じ内容をノートに書き写さない。

- 配置理由を一文で示し、ユーザーの合意を取ってからファイルを作る
- 既存ノートに同じ主題があれば、新規作成せず**そのノートを更新する**
- 必要以上にファイルを分割しない。ノート1枚で収まる場合はディレクトリを作らず `<業務名>.md` として直接置く。関連ノートが増えてきたら `<業務名>/README.md` を入口にして分ける
- `README.md` はそのディレクトリの入口・目次であり、ナレッジ本体を書く場所ではない
- ファイル名は、同じディレクトリの既存ノートと命名方針をそろえる（[getting-started.md](../../../docs/second-brain/getting-started.md) の「ファイル名」）

## 書き方

[getting-started.md](../../../docs/second-brain/getting-started.md) の「事実と自分の考え」に従い、次の4つを混ぜない。

- 確認できた事実
- ユーザーの判断・経験則（誰の判断か分かるように書く）
- AIからの提案
- 未確認事項

frontmatter は同ファイルの「メタデータ」の形式を使う。

- `source_notes` に根拠を残す。材料があればそのパスまたはURL、会話だけなら「本人からの聞き取り（YYYY-MM-DD）」
- `freshness` に鮮度を入れる

## 解像度チェック

下書きができたら、**教え返しの前にAI自身で判定する。** ユーザーに見せる前に、書いたものを読み直す。

1. 手順を1ステップずつ辿り、各ステップで「自分がいまこれを実行するとして、次に何をするか分かるか」を見る
2. 分からない箇所を全部挙げる。手順の何番で、7要素のどれが足りないかを書く
3. 「到達基準」の曖昧語と曖昧な動詞が本文に残っていないか探す
4. 詰まった箇所を質問する（最大5問）。答えを反映して1に戻る

**このループを最低1周は必ず回す。** 下書きをそのまま教え返しへ持っていかない。

2周しても埋まらない箇所は、ユーザーが答えられない箇所である。未確認事項に書き、**「ここはこのノートだけでは実行できない」とユーザーに伝える。**

## 教え返し

**毎回行う。** 作成したナレッジ**だけ**を根拠に、選択中のキャラクターで初任者へ説明する。キャラクター定義は `AGENTS.md` へ展開済みなので、追加で読むファイルはない。

説明は業務の要約ではなく、**手順を上から順に「次はこれをやる」と辿る形**にする。要約すると穴が隠れる。

ノートに書かれていないことは補完しない。**補完したくなった箇所が、そのナレッジの穴である。**

最後に理解度チェックを3問作る。**3問のうち少なくとも1問は判断基準を問う**（「〜のとき、どうするか」の形）。手順を覚えているだけでは答えられない問いを入れる。

## 差分確認

教え返しの結果を次の5つに分けて返す。

- 正しく説明できた内容
- 曖昧だった内容
- 矛盾した内容
- **このノートだけでは実行できないステップ**（手順の何番か）
- 次に確認すべき相手または資料

合意した修正だけを反映する。

## 成果物化

依頼があれば、リポジトリ直下の `outputs/` に引継ぎガイドを作る。元ナレッジへの相対リンクを入れる。`second-brain/` にはナレッジ本体だけを置く。

スライドにしたい場合は、このスキルでは作らず `make-my-slides` に渡す。

## ファイルの場所

リポジトリのルートから見た場所。存在確認のために何度もディレクトリを探さない。

```text
.agents/skills/teach-my-work/
  flows/         進め方ごとの手順書。選ばれた1つだけを読む
second-brain/    ナレッジ本体の置き場所
outputs/         引継ぎガイドなどの成果物
```

参照するファイル。同じ内容をこの SKILL.md や手順書に書き写さない。

- 分類の基準、保存しない情報、メタデータ、運用の決め方: [docs/second-brain/getting-started.md](../../../docs/second-brain/getting-started.md)
- Second Brain と PARA の考え方: [docs/second-brain/second-brain.md](../../../docs/second-brain/second-brain.md)
- 各置き場所の判断基準: `second-brain/<場所>/README.md`
- キャラクター定義: `AGENTS.md`（展開済み。追加で読まない）

## 完了条件

進め方によらず、次を満たしていること。

- 進め方と用途をユーザーと合意してから始めている
- 業務ナレッジが1つ作成または更新されている
- **「到達基準」を満たしている。** ノートだけを渡されたAIが次回この業務を実行できる
- **満たせなかった箇所は未確認事項に明示され、誰に聞けば埋まるかが書かれている**
- **解像度チェックを最低1周回している**
- 曖昧語（適宜、状況に応じて など）と、宛先のない動詞（確認する、共有する など）が本文に残っていない
- 置き場所を PARA の基準で説明でき、ユーザーが合意している
- frontmatter があり、`source_notes` から根拠をたどれる（会話だけの場合はそれが分かる）
- 確認できた事実、ユーザーの判断、AIの提案、未確認事項が区別できる
- 教え返しテストを実施し、差分をユーザーに返している
- 認証情報、個人情報、顧客の機密情報が含まれていない

手順書側に、その進め方に固有の完了条件が追加で書かれている。

## やらないこと

- 進め方と用途を聞かずに、質問を始める、または書き始める
- 3つの手順書を全部読む
- 材料の指定が無いのに、`inbox/` があるものと決めつけてディレクトリを探し回る
- 一度に6問以上聞く
- 聞いていないことをAIの一般論で埋める
- **「適宜」「状況に応じて」「確認する」のまま書いて、掘ったことにする**
- **解像度チェックを飛ばして教え返しに進む**
- **実行できない箇所を残したまま完了と報告する**
- 用途が「自分用」だからと言って、判断基準と例外を省く
- ノートに書いていないことを、教え返しで補って成立させる
- 未確認事項を消して、完成したように見せる
- ユーザーの合意を取る前にファイルを作る、移動する、削除する
