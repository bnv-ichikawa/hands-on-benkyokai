# 語り起こし型

頭の中にあるものを先に全部出してもらい、**整理はあとでやる**進め方。この進め方の中心は質問ではなく、**情報の分け方をユーザーと決めること**にある。

前提と共通ルールは [SKILL.md](../SKILL.md) にある。ここには段取りだけを書く。

## 段取り

### 1. 話してもらう

始める前に、次の4つを伝える。

- 順番も整理も気にしなくていい。思い出した順で話してよい
- 途中でAIは質問しないので、話が飛んでも構わない
- 認証情報や顧客名など、残したくない情報は話さないでほしい
- 話し終わったら「以上」と伝えてほしい

**話している間は遮らない。** 要約もしない。相槌で流れを止めない。

### 2. 復唱する

聞き取った内容を箇条書きで返す。**並べ替えず、話された順のまま返す。**

これは要約の工程ではなく、落ちがないかを確認する工程である。固有名詞、数字、条件は落とさない。

ユーザーの訂正と追加を受けてから次に進む。「そこはそういう意味じゃない」がここで出る。

### 3. 整理の仕方を決める

**ここがこの進め方の中心。** 論点を「何を話すか」から「どう分けるか」に移す。

決めることは3つ。

1. いくつのノートに分けるか
2. どの単位で分けるか
3. それぞれをどこに置くか

**案は1つだけ出さない。2案を出して選ばせる。** 分け方の候補には次のような軸がある。

| 分け方の軸 | 向いている場面 |
| --- | --- |
| 分けない（1枚にまとめる） | 話された範囲が1つの業務に収まっている |
| 業務単位で分ける | 複数の業務の話が混ざっている |
| 手順と判断基準で分ける | 手順は変わりやすいが、判断基準は長く使える |
| 進行中の案件と、継続業務で分ける | 一方は `projects/`、もう一方は `areas/` になる |

置き場所の判断は [SKILL.md](../SKILL.md) の「配置」に従う。**AIが決めて進めない。合意を取ってから下書きする。**

### 4. 不足を掘る

整理の枠が決まってから質問する。枠が決まる前に質問すると、どのノートに入る情報かが分からないまま話が増える。

**1回5問で終わらせない。** 語りは全体像が出る代わりに、細部が飛んでいるのが普通。ノートごとに [SKILL.md](../SKILL.md) の「実行できる状態の7要素」を当て、空いている要素を5問ずつ何巡か聞く。

語りに特有の空き方は次の3つ。優先して聞く。

- **順番**: 話の順が実際の実行順とずれている。「これは〜の前ですか、後ですか」
- **判断の言語化**: 慣れている人ほど分岐を無意識にやっている。「そこで別のやり方に切り替えるのは、どういうときですか」
- **場所**: 「あのシート」「例のチャンネル」のような指示語。具体名とURLに置き換える

止める条件は [SKILL.md](../SKILL.md) の「掘るのをやめる条件」に従う。

### 5. 下書き

[SKILL.md](../SKILL.md) の「書き方」に従う。`source_notes` は「本人からの聞き取り（YYYY-MM-DD）」とする。

ノートを複数作った場合は、相互にリンクを張る。

### 6. 解像度チェック

[SKILL.md](../SKILL.md) の「解像度チェック」を最低1周回す。**ノートを複数作った場合は、ノートごとに回す。**

分けたことで手順が途中で切れていないかも見る。ノートAの続きがノートBにある場合、リンクだけでなく「ここから先は〜へ」の一文を入れる。

### 7. 教え返し

[SKILL.md](../SKILL.md) の「教え返し」に従う。ノートが複数ある場合、どのノートを使うかを決めてから説明する。

### 8. 差分確認

[SKILL.md](../SKILL.md) の「差分確認」に従う。

### 9. Skill化

AIに業務を任せる場合は、[SKILL.md](../SKILL.md) の「Skill化」に従い、業務ナレッジからSkillを作る。新しいAIセッションでテストし、止まった箇所を直す。

### 10. 成果物化

依頼があれば行う（[SKILL.md](../SKILL.md) の「成果物化」）。

## この進め方での注意

- **話している途中で質問を挟まない。** 思い出す流れが切れる。疑問はメモしておき、段取り4でまとめて聞く
- **全部話し終わった時点を、材料が揃った時点と取り違えない。** 語りは網羅的に見えて解像度が浅い。段取り4を省略しない
- 復唱で要約しすぎない。まとめた結果、ユーザーが「言ったことが消えた」と感じると訂正が出なくなる
- 話の中の**事実 / ユーザーの判断 / 感想や愚痴**を分けて扱う。感想は保存しないか、経験則として残すかをユーザーに聞く
- 1回の語りに複数の業務が混ざるのが普通。無理に1ノートへ押し込まない
- 整理案を2案出すとき、AIの推し案は理由を添えて先に置く。ただし選ぶのはユーザー
- 話されたが保存しないと決めた内容は、黙って落とさない。落とすことをユーザーに伝える
- 分け方が決まらない場合、無理に分類せず `inbox/` に1枚で置き、何が決まれば動かせるかを書く

## 固有の完了条件

[SKILL.md](../SKILL.md) の完了条件に加えて、次を満たしていること。

- 復唱に対するユーザーの訂正を反映している
- ノートの分け方を、2案以上の中からユーザーが選んでいる
- **語りの中の指示語（「あのシート」「例のチャンネル」）が具体名に置き換わっている**
- **手順の順番が、実際の実行順としてユーザーに確認されている**
- ノートを複数作った場合、相互にリンクが張られ、手順が途中で切れていない
- 保存しないと決めた内容がある場合、その判断をユーザーが知っている
- `source_notes` が「本人からの聞き取り（日付）」になっている
