# 進め方: たたき台型

最小限だけ聞いて、**一度最後まで作る。** 完成品を見てから修正を指示してもらう。

前提（題材の扱い、安全確認、画像の見せ方、文字数の上限、ファイルの場所）は [SKILL.md](../SKILL.md) にある。ここには書かない。

```text
STEP 1  足りない前提だけを1回で聞く
STEP 2  全枚の内容を作る
STEP 3  成果物と「推測で埋めた箇所」を渡す
STEP 4  指示された箇所だけ直す（繰り返し）
```

この進め方では合意ゲートを置かない。代わりに **STEP 3 で「どこが推測か」を必ず開示する**。開示しないと、ユーザーは何を確認すべきか分からないまま完成品を受け取ることになる。

---

## STEP 1. 足りない前提だけを1回で聞く

すでに [SKILL.md](../SKILL.md) の最初のメッセージで、題材・メモの有無・進め方・成果物の形は聞いている。**同じことを聞き直さない。**

追加で必要なのは次の2つだけ。**1回のメッセージでまとめて聞き、これ以上は聞かない。**

1. **持ち時間は何分か**（枚数が決まる）
2. **誰が聞くか**（前提知識の水準が決まる）

見た目は公式スライドマスタで決まっているため、**型を選ばせる必要はない。** 聞かない。

「不明」「おまかせ」と返ってきた項目は、次の既定で進める。**勝手に決めたことは STEP 3 で必ず開示する。**

| 項目 | 既定 |
| --- | --- |
| 持ち時間 | 10分（15〜20枚） |
| 聞き手 | 社内の同僚。専門用語は補足付きで使う |

ここで質問を止める。**中身を1枚ずつ聞かない。** それはすり合わせ型のやり方であり、この進め方の意味がなくなる。

---

## STEP 2. 全枚の内容を作る

1. `outputs/<資料名>.json` に**全枚**を書く。JSON形式は [tools/make-pptx/README.md](../../../../tools/make-pptx/README.md)
2. 導入 → 課題 → 内容 → まとめ の順に組む
3. 締めの前に、出典と未確認事項の枚を置く

文字数の上限は [SKILL.md](../SKILL.md) の表に従う。**表紙のタイトルは16文字以内。** 超えると副題と重なる。

### 材料が足りない枚の埋め方

たたき台型では、材料が足りなくても止まらずに書く。ただし**埋め方に決まりがある。**

| 種類 | 埋めてよいか | 書き方 |
| --- | --- | --- |
| 話の流れをつなぐ一般論 | よい | 普通に書く。あとで直せる |
| 構成上あるべき見出し | よい | `title` と `lead` だけ置き、`bullets` は2〜3項目の骨組みにする |
| **数字**（金額、件数、割合、期間） | **だめ** | `（要確認）` と書く。数字を発明しない |
| **固有名詞**（会社名、製品名、人名、部署名） | **だめ** | `〇〇社` `担当部署` のように役割で書く |
| 因果関係や成果の断定 | だめ | 「〜と考えている」と主体を付ける、または `未確認` を付ける |

**埋めた箇所は必ず記録しておく。** STEP 3 でそのまま一覧にする。

### 書き出し

最初に合意した形で、利用可能な手段があれば `.pptx` 化する。このリポジトリにはローカル実行用スクリプトを同梱していないため、存在しない `tools/make-pptx/*.ps1` を実行しない。

画像またはスライドを確認できる場合は、自分の目で確認する。確認できない場合は、確認できていないことをユーザーへ明示する。

- 枚数が合っているか
- タイトルが折り返して副題や本文と重なっていないか
- 表が白いコンテンツ面からあふれていないか
- 文字が四角（□）になっていないか

崩れていた場合は JSON または元の構成を直してもう一度作る。

---

## STEP 3. 完成品と「推測で埋めた箇所」を渡す

渡すものは3つ。**3つ目を省かない。**

1. 成果物の場所（合意した形のファイル）
2. 見た目を確認できた場合は、表紙と代表的な本文1枚
3. **推測で埋めた箇所の一覧**

一覧はスライド番号付きで、確認しやすい形にする。

```text
できました。outputs/<資料名>.json（全18枚）
.pptx 化した場合は PowerPoint で開いて、文字はそのまま直せます。

[表紙と本文の画像を貼る]

次の箇所は、材料が無かったのでこちらで補いました。確認してください。

  勝手に決めた前提
    持ち時間  10分と想定（18枚）
    聞き手    社内の同僚と想定

  中身を補った枚
    6枚目「現状の課題」    一般論で骨組みだけ書いた
    9枚目「他社の事例」     材料に無いのでAIからの提案として書いた

  数字・固有名詞を伏せた箇所
    7枚目   導入時期を（要確認）にした
    11枚目  取引先名を「〇〇社」にした

直したい箇所を、枚数を添えて教えてください。
細かい文字の調整なら、PowerPoint で直接直してもらうほうが早いです。
```

この一覧が、そのまま修正指示のチェックリストになる。

---

## STEP 4. 指示された箇所だけ直す

修正のたびに次を守る。

- **指示された箇所だけを直す。** 指摘されていない箇所を、良くなりそうだからと書き換えない
- JSON を直してから作り直す
- 見た目を確認できる場合は、直した枚が崩れていないか確認する
- 何枚目をどう直したかを一言で報告する

**ユーザーが PowerPoint 側で仕上げ始めたら、そこから先は pptx が正本になる。** JSON から作り直すと上書きされるため、作り直す前に必ず確認する。

枚数や構成そのものを変える指示が来た場合は、変更後の枚数だけ先に伝えて了解を取る。全体の作り直しは、ユーザーがそう言った場合だけにする。

「もっと細かく相談しながら詰めたい」と言われたら、[step-by-step.md](step-by-step.md) を読んで切り替える。いまの成果物を引き継ぎ、作り直さない。

---

## この進め方に固有の完了条件

[SKILL.md](../SKILL.md) の共通の完了条件に加えて、次を満たしていること。

- 推測で埋めた箇所、勝手に決めた前提を、枚数付きで開示している
- 数字と固有名詞を発明していない（`（要確認）` か役割名になっている）
- 修正は指示された箇所だけに閉じている

## この進め方でやらないこと

- 中身を1枚ずつ聞いて回る（それはすり合わせ型）
- 推測で埋めた箇所を黙って渡す
- 数字や固有名詞をもっともらしく作る
- 指示されていない箇所を、ついでに直す
- ユーザーが PowerPoint で仕上げた pptx を、確認せずに JSON から作り直す
