# 進め方: すり合わせ型

段階ごとに合意を取りながら進める。**合意なしで次の段階へ進まない。**

前提（題材の扱い、安全確認、画像の見せ方、文字数の上限、ファイルの場所）は [SKILL.md](../SKILL.md) にある。ここには書かない。

```text
STEP 1  目的と分量を決める              ← ゲート A
STEP 2  構成案に合意する                ← ゲート B
STEP 3  表紙と2枚目を試作して見せる       ← ゲート C
STEP 4  残りの本文を書く
STEP 5  仕上げて渡す
```

各段階の冒頭で、いま何段目にいるかを一言で伝える。**ゲートを2つまとめて通さない。**

ユーザーが「全部おまかせ」と言った場合も、ゲート B・C は飛ばさない。ただし選択肢を絞って提示し、判断の負担を下げる。それでも細かすぎると言われたら、たたき台型（[draft-first.md](draft-first.md)）への切り替えを提案する。

---

## STEP 1. 目的と分量を決める ── ゲート A

次の観点から最大4問をまとめて質問する。ユーザーが「不明」「まだ決めていない」と答えられる形にする。

- 何のための発表か（聞き終わったあと、聞き手にどうなってほしいか）
- 誰が聞くか（前提知識のばらつき、専門用語が通じる範囲）
- 持ち時間は何分か（質疑を含むか）
- 一番伝えたいことは何か（1文で）

成果物の形は [SKILL.md](../SKILL.md) の最初のメッセージで合意済みなので、**聞き直さない。**

「不明」と返ってきた項目は勝手に決めない。次の構成案で `未確定` として見せ、判断を仰ぐ。

持ち時間から枚数の目安を決めて伝える。目安の表は [references/writing.md](../references/writing.md) にある。目安を超える情報量なら、削る候補を先に相談する。

**ゲート A の合意事項**: 一番伝えたいこと1文と、枚数の目安。

---

## STEP 2. 構成案に合意する ── ゲート B

スライドのタイトルと、各枚に使うレイアウトだけを並べる。**この段階では本文を書かない。ファイルもまだ作らない。**

```text
 1  表紙                          cover
 2  今日のゴール                   content
 3  なぜこの話をするか              content
 4  第1章 ○○                     section
 5  ...                          content
 n-1 出典と未確認事項              content
 n  締め                          closing
```

確認してもらうこと。

- タイトルを上から読むだけで話の流れが分かるか
- 導入 → 課題 → 内容 → まとめ から外れる場合、その理由に納得できるか
- 材料に無い話を足す場合、それは採用してよいか（「AIからの提案」と明示する）
- 削る候補と、その理由

合意が取れるまで本文へ進まない。ユーザーが構成を書き換えた場合は、書き換えた側を正とする。

**ゲート B の合意事項**: スライドのタイトル一覧と枚数。

---

## STEP 3. 表紙と2枚目を試作して見せる ── ゲート C

**いきなり全枚を書かない。** まず2枚だけ作り、実物を見せる。

1. `outputs/<資料名>.json` を作り、**表紙と2枚目だけ**を書く。JSON形式は [tools/make-pptx/README.md](../../../../tools/make-pptx/README.md)

   ```json
   {
     "slides": [
       { "type": "cover", "title": "16文字以内", "subtitle": "発表者 ｜ 2026年MM月DD日" },
       { "type": "content", "title": "今日のゴール", "lead": "この枚で言いたいこと。",
         "bullets": ["1つ目", "2つ目", "3つ目"] }
     ]
   }
   ```

2. 利用可能な手段があれば試作を `.pptx` 化し、画像またはスライドとして確認する。このリポジトリにはローカル実行用スクリプトを同梱していないため、存在しない `tools/make-pptx/*.ps1` を実行しない
3. 確認できる場合は、自分の目で確認してからユーザーへ見せる。確認できない場合は、確認できていないことを明示する
4. 試作内容を見せて次を聞く

   - タイトルの文言はこれでよいか（表紙は16文字以内、超えると副題と重なる）
   - 発表者名・日付は正しいか
   - 見た目の方向性はこれでよいか

崩れていた場合は JSON を直してから作り直す。

ここで見た目が固まるので、以降で見た目の相談が起きなくなる。

**ゲート C の合意事項**: 表紙の文言と、資料全体の見た目。

---

## STEP 4. 残りの本文を書く

合意した構成だけを使い、3枚目以降を JSON に足す。

材料が聞き取りだけの場合、**構成に対して中身が足りないことが多い。** 足りない枚は推測で埋めず、その枚を挙げて中身を聞く。1回に最大5問まで。

```text
次の3枚は、まだ話す中身が決まっていません。それぞれ2〜3行で教えてください。
  4枚目「現状の課題」
  6枚目「どう変えるか」
  8枚目「次にやること」
```

守ること。詳しくは [references/writing.md](../references/writing.md)。

- 1枚1メッセージ
- `lead` にその枚の主張を1文だけ書く
- 箇条書きは5項目まで、1項目40文字以内
- 表は6行×4列まで
- 材料に無い事実を追加しない
- 未確認の内容は断定しない
- 締めの前に、出典と未確認事項の枚を置く

書き終えたら、スライドのタイトルと各枚で話す一言を順に読み上げ、ユーザーと次を確認する。

- 流れが自然か
- 持ち時間に収まるか
- 事実と、ユーザーの判断と、AIからの提案が混ざっていないか

指摘された箇所だけを直す。指摘されていない箇所を、良くなりそうだからと書き換えない。

---

## STEP 5. 仕上げて渡す

最初に合意した形で、利用可能な手段があれば書き出す。

画像またはスライドを確認できる場合は、自分の目で確認する。確認できない場合は、確認できていないことを完了報告に書く。

- 枚数が合っているか
- タイトルが折り返して重なっていないか
- 表が白いコンテンツ面からあふれていないか
- 文字が四角（□）になっていないか

崩れていた場合は JSON を直してもう一度作る。

渡すときに次を伝える。

- `outputs/<資料名>.json` の場所
- `.pptx` 化した場合は `outputs/<資料名>.pptx` の場所
- **PowerPoint で開いて文字を直せる**こと
- 大きく直す場合は、こちらに言えば JSON から作り直せること
- ただし**PowerPoint 側で仕上げたあとは pptx が正本**になるので、その後 JSON から作り直すと上書きされること

---

## この進め方に固有の完了条件

[SKILL.md](../SKILL.md) の共通の完了条件に加えて、次を満たしていること。

- ゲート A・B・C の3つで、それぞれ個別に合意を取っている
- 構成案の段階では本文を書いていない
- 表紙と2枚目をユーザーが画像で確認したうえで、残りを書いている

## この進め方でやらないこと

- ゲートを2つ以上まとめて通す
- 構成案の合意を飛ばして全枚を生成する
- 試作を見せる前に全枚の JSON を書く
