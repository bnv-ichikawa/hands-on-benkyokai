# Make My Slides

メモ、または会話で聞き取った内容を、PowerPoint スライド用の構成と本文へ変える。

このファイルは**入口**である。共通の前提と進め方の選択だけを扱い、実際の手順は選ばれた1つの手順書に書いてある。

## 作り方の全体像

公式スライドマスタ（`表紙` / `コンテンツ1` などのレイアウト）に載せ替えやすい内容を作り、利用可能な手段で `.pptx` 化する。

```text
内容を deck.json に書く
  → 利用可能なプレゼンテーション作成手段で .pptx 化する
  → outputs/ に成果物を置く
```

この作り方の意味。**ユーザーに聞かれたら答えられるようにしておく。**

- **文字が編集できる。** 各ページは画像ではなく本物のテキストボックス。渡した相手が直せる
- **公式マスタに合わせやすい。** 配色やロゴを手で似せるのではなく、公式マスタへ載せ替える前提で構成する
- **生成手段を固定しない。** このリポジトリにはローカル実行用スクリプトを同梱しない

内容のJSON形式は [tools/make-pptx/README.md](../../../tools/make-pptx/README.md) にある。同じ内容をこのファイルや手順書に書き写さない。

## 1. 最初のメッセージで4つ聞く

いきなり作り始めない。次の4つを**1回のメッセージ**でまとめて聞く。

1. **何についてのスライドか**（1〜2行で）
2. **元になるメモやノートはあるか**（あればその場所。無ければ会話から作る）
3. **どちらの進め方にするか**（下の「進め方」の表を見せる）
4. **最後に何の形で欲しいか**（下の「成果物の形」の表を見せる）

### 進め方

| 進め方 | どう進むか | 向いている場面 |
| --- | --- | --- |
| **すり合わせ型** | 構成 → 表紙の試作 → 本文 と区切って合意を取りながら進む | 内容が固まっていない。人に見せる資料で、手戻りを避けたい |
| **たたき台型** | 最小限だけ聞いて、AI が一度最後まで作る。完成品を見てから修正を指示する | だいたい決まっている。まず形を見てから考えたい |

決まらない場合は**すり合わせ型**を既定にし、理由を一文添える。手戻りが少ないため。

### 成果物の形

| 欲しいもの | 渡すもの | 補足 |
| --- | --- | --- |
| PowerPointで開いて自分で仕上げたい | `.pptx` | 既定。**文字を直接編集できる** |
| 印刷する、そのまま配る | `.pptx` + `.pdf` | PDF は PowerPoint 側で書き出す |
| Google スライドで共同編集する | `.pptx` をアップロード | Drive で「Google スライドとして開く」。**文字も編集できる** |

正本は `outputs/<名前>.json`（内容）と `outputs/<名前>.pptx`（成果物）である。細かな仕上げをユーザーが PowerPoint 側で行った場合は、**そこから先は pptx が正本になる。** JSON を作り直して上書きしない。

以下はどちらの進め方でも共通の決まりである。

## 題材の扱い

- **題材の指定がない呼び出しでは、メモは無いものとして扱う。** ファイルを探しに行かない
- ファイルを指定された場合だけ、それを読む。見つからなければ探索範囲を広げず、場所を1回聞く
- `second-brain/` の中を見に行くのは、ユーザーが「あのメモから作って」のように**そこにある前提で話したときだけ**
- メモを読んだ場合は、言えそうなことを3行以内で要約して返す。読み違いをここで見つける
- 会話だけで作る場合、聞き取った内容がこの資料の唯一の材料になる

## 安全確認

材料に認証情報、個人情報、顧客の機密情報がないか確認する。見つけた場合は内容を引用せず、匿名化または除去を依頼して作業を止める。

判断基準は [getting-started.md](../../../docs/second-brain/getting-started.md) の「3. 保存しない情報を決める」を使う。

スライドは会議や社外で共有される前提のため、業務ナレッジより厳しく判断する。ナレッジには残してよい社内固有名も、スライドでは役割名へ置き換えるかを確認する。

## 画像の見せ方

書き出した PNG をユーザーに見せるときは、**パスを文章で書くのではなく画像そのものを送る。**

- Markdown の画像記法で貼る: `![表紙](C:/Users/.../outputs/my-deck.001.png)`
- 区切りは `/` を使う。`\` を含むパスは画像として表示されない
- コードブロックの中に入れると表示されないので、本文に直接書く

## ファイルの場所

リポジトリのルートから見た場所。存在確認のために何度もディレクトリを探さない。

```text
.agents/skills/make-my-slides/
  flows/                          進め方ごとの手順書。選ばれた1つだけを読む
  templates/bnv-master/           公式マスタから作ったテンプレート
  references/                     書き方の基準
outputs/                          成果物
```

- 内容のJSON形式: [tools/make-pptx/README.md](../../../tools/make-pptx/README.md)
- 書き方の基準（分量・文字数・事実と判断の区別）: [references/writing.md](references/writing.md)

## 分量と文字数の上限

公式レイアウトのプレースホルダーには決まった幅がある。**超えると折り返して重なる。**

| 対象 | 上限 | 理由 |
| --- | --- | --- |
| 表紙のタイトル | **16文字**（2行まで） | 幅 401pt しかなく、3行になると副題と重なる |
| 本文のタイトル | 24文字（1行） | 上のネイビー帯に収める |
| リード文 | 1文・50文字 | |
| 箇条書き | 5項目・1項目40文字 | |
| 表 | 6行 × 4列 | |

そのほかの基準は [references/writing.md](references/writing.md) にある。

## 書き出しと目視確認

`.pptx` 化できる手段が利用可能な場合だけ、成果物を書き出す。このリポジトリにはローカル実行用スクリプトを同梱していないため、存在しない `tools/make-pptx/*.ps1` を実行しない。

画像またはスライドを確認できる場合は、必ず自分の目で確認する。確認できない場合は、確認できていないことを完了報告に書く。

- 枚数が合っているか
- タイトルが折り返して副題や本文と重なっていないか
- 表が白いコンテンツ面からあふれていないか
- 文字が四角（□）になっていないか

崩れていた場合は JSON または元の構成を直してもう一度作る。pptx を直接いじって直した場合は、そこから先は pptx を正本として扱う。

うまくいかない場合は、**PowerPoint が入っているかを確認する。** 入っていない環境ではこの方法は使えないので、その旨を伝える。

## 完了条件

- `outputs/` に内容の JSON がある。`.pptx` 化まで頼まれ、利用可能な手段がある場合は `.pptx` も揃っている
- 可能な範囲で見た目を確認し、確認できない場合はその旨を伝えている
- 出典（メモがある場合は場所、無い場合は「本人からの聞き取り」）と未確認事項が分かる
- 枚数と文字数が持ち時間に見合っている
- 認証情報、個人情報、顧客の機密情報が含まれていない

手順書側に、その進め方に固有の完了条件が追加で書かれている。

## やらないこと

- 進め方と成果物の形を聞かずに作り始める
- 両方の手順書を読む
- 題材の指定が無いのに、メモがあるものと決めつけてディレクトリを探し回る
- 材料に無い数字や固有名詞を足す
- 見た目を確認せずに完了と報告する
- 上限文字数を超えたまま作る（折り返して重なる）
- ユーザーが PowerPoint 側で仕上げた pptx を、JSON から作り直して上書きする
